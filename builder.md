# builder.md

Guidance for any AI assistant (ChatGPT, Claude, or otherwise) helping build content and features on Chaos-Server.

**Read `CLAUDE.md` first** — it covers build/test/run commands, solution layout, the entity hierarchy, configuration cascade, testing conventions, and coding standards. This file doesn't repeat any of that; it captures conventions and pitfalls that only show up once you've actually built things in this repo, so a new assistant doesn't have to rediscover them the hard way.

## Multi-agent development workflow (read this before touching anything)

This project uses more than one AI assistant across two different roles. Getting the roles straight matters — the failure mode to avoid is one agent designing something, a person designing another version of the same thing, and a third agent inventing yet another answer, with nobody agreeing on which one is real.

**Team 1 — Design & Implementation.** The human + a chat-based design assistant work through classes, abilities, progression, economy, devotion, balance, and architecture *in conversation*, until something is genuinely locked. Once it's locked, it goes to an implementation agent as a focused task inside the actual repo. If the implementer hits something unknown in the codebase mid-task, it investigates and reports back — it does not guess or silently decide; the real decision gets made back in the design conversation, then a fresh task goes out.

**Team 2 — Production, automation, and assets.** Once designs are locked, a second team handles turning them into content at scale: maintaining technical workflows/documentation, orchestrating repetitive production work, and generating/editing pixel art under Dark Ages' visual constraints. This team is most valuable *after* Team 1 has locked something, not before — it shouldn't be inventing design, only executing it.

**The one rule that matters more than which specific tool fills which role:** every agent must be told explicitly, every time, whether it is **executing a locked design** or **proposing options for a design that isn't locked yet**. Confusing the two is exactly how three different, mutually-incompatible versions of the same feature end up half-built. `builder.md` and the project's `ELYSIUM_*_DESIGN.md` docs are the single source of truth — an agent's own memory of a past conversation, or its own inference about what "probably" was intended, is not.

**On which tool actually does the implementing:** don't assume a tool is right for the implementer role just because it's available — earn it through results. As of this session, the implementation-agent role has been proven out extensively on this exact codebase (dozens of complex, multi-round tasks, real bugs caught via genuine test-driven verification, not just "builds clean"). A second tool used purely for capacity/overflow on cleanly-separated work (a different system entirely, no shared files) is a reasonable parallel-track addition, but should not be assumed equally deep on this specific codebase's conventions until it's demonstrated the same track record.

**Practical shape of the loop:**
1. Design conversation locks a spec (e.g. "Bastion's 12 abilities, floor schedule, and mechanics are final").
2. A focused, self-contained task brief goes to the implementer — pointing at the exact locked doc section, not a paraphrase.
3. Implementer investigates existing codebase state before writing new content, flags genuine ambiguity rather than guessing, and stops at real checkpoints for anything involving a judgment call.
4. Findings/ambiguities come back to the design conversation for a real decision.
5. Implementer proceeds with the resolved decision, tests for real (functional assertions, not just "no exceptions"), and reports.
6. **Anything discovered during implementation that a DIFFERENT future task would benefit from knowing gets added to `builder.md` as part of the same pass** — not the fact that a feature got built (that's just commit history), but a reusable pattern, a gotcha, a shared chokepoint, or a "don't do X, do Y instead" lesson. If the next agent working on an unrelated feature would hit the same wall or benefit from the same shortcut, it belongs here. If it's genuinely one-off and won't matter again, it doesn't — keep this file useful, not a changelog.
7. Nothing gets committed without being explicitly asked, same as always.
8. Once core systems/abilities/content are locked and implemented, focus can shift to the production/asset team — visual design work makes more sense once there's a stable target to design *for*, not before.

## Content authoring: where things go

`Data/Configuration/Templates/` is organized by class/type, not flat:

- `Skills/<Class>/` — e.g. `Skills/Berserker/cyclone.json`. `Skills/Universal/` holds class-agnostic base skills (assail, ambush, twohandedattack).
- `Spells/<Class>/` — e.g. `Spells/Mystic/quick_mend.json`. Empty class folders (`Lancer/`, `MartialArtist/`) exist on purpose for classes with no unique spells yet.
- `Monsters/Enemies/` — real combat monsters. `Monsters/Spawned/` — skill/spell-spawned entities (decoys, shrines, hazards, dust devils) that are never placed by a map spawner directly.
- `Items/` has its own subfolders by slot (Helms, Weapons, etc.) — check neighboring files for the pattern before adding a new one.

**Template loading is recursive and keyed by filename, not path.** `Recursive: true` is set for every template cache in `appsettings.json`, and lookups match by `templateKey` (the filename, case-insensitive), scanned across all subfolders. This means:
- You can reorganize folders freely without updating any `scriptKeys`/`skillTemplateKeys`/`spellTemplateKeys`/loot table references — they're all string keys, not paths.
- Two files with the same basename anywhere under the same template root *will* collide silently (first match wins) — keep names unique within a template type.

## The #1 pitfall: `ConfigurableScriptBase` requires a matching `scriptVars` entry

Every skill/spell/effect script picks one of two base classes:

- `Configurable*ScriptBase` (e.g. `ConfigurableSkillScriptBase`) — for scripts with tunable values. The constructor does `subject.Template.ScriptVars[scriptKey]` and **throws `NullReferenceException` at construction time** if the template's `scriptVars` JSON has no entry under that script's key. The exception message says exactly this: *"If this script has no configurable variables, do not use a ConfigurableScript."*
- Plain `*ScriptBase` (e.g. `SkillScriptBase`) — for scripts with zero configurable values (hardcoded constants, or pure pass-through/placeholder scripts). No `scriptVars` requirement at all.

**Rule of thumb:** if the script class has no `#region ScriptVars` block of public settable properties, it must not extend a `Configurable*ScriptBase`. This is an easy mistake when copy-pasting a script as a starting point — the crash won't show up until something actually constructs that specific `Skill`/`Spell`/`Effect` instance (e.g. a player who has the skill logs in), so it can pass a build and even a server boot silently before biting in production.

Note the default `CanUse()` differs between the two: `Configurable*ScriptBase` defaults to `true` (always usable), plain `*ScriptBase` defaults to `context.Source.IsAlive`. Switching base classes to fix the above can subtly tighten this — usually the more correct behavior (dead characters generally shouldn't be able to use skills), but worth knowing it's not purely cosmetic.

## Common patterns worth reusing rather than reinventing

- **`EffectBase` lifecycle**: `OnApplied()` / `OnTerminated()` / `Update(TimeSpan)` / `ShouldApply(source, target)` (return `false` to reject application — base impl blocks a same-name/same-icon conflicting effect). `SetDuration()` sets how long it lasts.
- **Tag-based AI gating**: `Subject.Trackers.Tags` (a `ConcurrentDictionary<string,string>`) is the standard way to make a status effect suppress monster AI behavior. `WanderingScript.cs` and `AggroTargetingScript.cs` already check tags like `"stasis"`, `"rooted"`, `"asleep"`, `"feared"`, `"vanished"` — add a new tag there rather than inventing a parallel mechanism.
- **Passive class mechanics** (rage, chi, resource-on-hit systems): implemented as an `AislingScript` that no-ops unless `Subject.UserStatSheet.AdvClass == AdvClass.X`, ticking every `Update(TimeSpan delta)`. See `BerserkerRageScript.cs` for the reference shape: builds a resource on hit, decays it when idle, syncs a scaling stat bonus, and drives tiered visual auras — all in one script, no need to hook the damage pipeline directly for the stat-bonus part.
- **Damage pipeline hooks** (shields, counters, on-hit procs, damage-taken modifiers): `Chaos/Scripting/FunctionalScripts/ApplyDamage/ApplyAttackDamageScript.cs` is the shared choke point for all attack damage. It already has an `if/else if` chain of tag/effect checks in the Aisling case (Veil, Shrine shield, Bubble shield, Lancer's Shield, Counter Strike, Phoenix Rise) — add new "block/negate/redirect damage" mechanics as another branch here, not as a bolt-on effect that tries to intercept damage on its own.
- **True invulnerability/damage negation**: don't rely on a huge negative AC bonus. Aisling AC and Monster AC are clamped to *separate*, independently-configured floors (`WorldOptions.MinimumAislingAc` vs `MinimumMonsterAc`) — a `-10000` AC trick that fully negates damage for a monster will NOT do the same for a player, since the Aisling floor is far less extreme. For a player-side "block", set a tag and short-circuit the damage in `ApplyAttackDamageScript` instead.

## CC and visual-feedback gotchas (found while fixing per-class playtest bugs)

- **`RestrictionBehavior` (`Chaos/Scripting/Behaviors/RestrictionBehavior.cs`) is the shared CC enforcement chokepoint.** Root/Blackout/Lullaby/Stasis/Silence all gate through it on the Aisling side (`DefaultAislingScript.cs` wires it up) rather than each effect reimplementing its own "can I move/act" check. Add new CC types here, not as one-off tag checks scattered across scripts.
- **There is no single "stun" effect** - `RootEffect` blocks movement only (can still attack/cast), `BlackoutEffect` blocks attacking/casting only (can still move). Neither is a true full stun by itself, and the codebase is not consistent about which one an ability's description calls "stun" (e.g. Pinpoint Shot's "briefly stuns" applies Blackout; Predator's Pounce/Shield Thrust's "stun" applies Root). Pick based on what the ability actually needs to prevent, or apply both for a real full stun - don't assume "stun" means one specific effect class.
- **A one-shot `Animate()` call in `OnApplied()` is not a persistent visual.** It plays once and fades on the client well before a multi-second effect actually ends, so anything meant to look "ongoing" needs a `SinceLastAnimation` timer re-triggered from `Update(TimeSpan delta)` (see `MarkOfTheBaneEffect`/`DeathMarkEffect`/`MarkedForValhallaEffect` for the exact shape - `StasisEffect` established the pattern first). This has now hit 3 unrelated marked-target effects across 3 different classes; if you're building a new debuff/mark meant to stay visibly "active" on a target, use the re-animate-on-a-timer shape from the start rather than an apply-once `Animate()`.
- **`IsWalkable(point, ...)` only checks the destination tile, not the path to it.** Any ability that computes a fallback landing point further away than the first candidate (e.g. "try 1 tile back, else try 2 tiles back") without validating the tiles in between can teleport straight through a 1-tile-thick wall, since the intermediate tile is never checked. If you need multi-tile displacement, either walk it tile-by-tile checking each step (`IsWall`/`IsBlockingReactor`/occupancy per tile, see `ShieldThrustScript`'s knockback loop) or make sure a blocked near tile actually stops the attempt instead of trying a farther one.
- **A resource bar can be deliberately repurposed as a non-resource visual indicator** (e.g. Lancer's Shield spends MP as "shield charge"; Severance's stack count is displayed by scaling the caster's MP bar 0-100 in `SeveranceTargetSync`). This is an intentional, established pattern in this codebase, not a bug by itself - but it only works cleanly for a single tracked target/value. If more than one ability can drive the same repurposed bar, every one of them needs to go through the same sync helper (`SeveranceTargetSync.SwitchTargetIfNeeded`/`SyncMpToStacks`), or some of them will silently update real state without ever moving the bar the player is watching, which reads as "this mechanic doesn't work" even though the underlying stacking/tracking is fine.
- **"Always-on passive gated only by `BaseClass`/`AdvClass`" was a recurring (and ultimately unwanted) pattern for several class passives** (Valkyrie's Divine Verdict/Wings of Stacia/Chooser of the Slain/Divine Fury, Berserker's Unbroken) - these fired for every character of that class regardless of whether the specific passive skill/spell entry was ever learned. The real fix, once confirmed: gate on `Subject.SkillBook.ContainsByTemplateKey("the_passive_key")` (or `SpellBook`, same method) in addition to the class check - see `ExecuteIndicatorScript`/Assassin's Bloodlust auto-trigger for the pre-existing correct examples, and the fixed Valkyrie scripts for the retrofit shape. "True passives" (display-only, no real cast) still get a real templateKey and still get added to the SkillBook/SpellBook via `ComplexActionHelper.LearnSkill`/`LearnSpell` (routed to `PageType.Page3`, the H tab) - `IsPassive` on the template controls that routing, it doesn't mean "skip the book entirely." If you're wiring a new always-on class mechanic, gate it on the learned-check from the start.
- **`EffectBase.ShouldApply`'s default rejects reapplication of any effect sharing the same `Name` OR the same `Icon` as one already on the target**, and silently sends the target's attacker an orange "Target is already affected by X" message when it does. This is correct for genuinely one-shot debuffs, but wrong for anything meant to refresh/re-trigger repeatedly while already active (a repeating proc-based mark, a stacking effect) - those need an explicit `override bool ShouldApply(...) => true`. Has hit 4 abilities now (Severance, Mark of the Bane, Marked for Valhalla, Shadowmark) - if a new mark/debuff is meant to be reapplied by its own class's other abilities while already up, add the override from the start rather than waiting for a "the orange message keeps popping up" report. Also note two *different* effects that happen to share an `Icon` byte will block each other under this same default - worth checking for collisions when picking an icon for a new effect.
- **A "guaranteed" damage number (execute effects, true damage) still gets AC-mitigated if passed straight to `ApplyDamage`** - the shared pipeline (`DamageFormula.Calculate` inside `ApplyAttackDamageScript.ApplyDamage`) always applies the target's AC multiplier to whatever raw `damage` int it receives, so "3x current HP" isn't actually a guaranteed kill against a high-AC target, it's just a big mitigated number. `DefenseIgnoreHelper.ApplyIgnoreDefense(target, rawDamage, ignorePct)` (originally built for Slayer's defense-ignoring strikes) pre-compensates the raw value so the pipeline's own AC multiply lands at the desired effective mitigation - pass `1.0m` for a fully unmitigated true hit. Use this for any "should bypass defense" mechanic instead of just inflating the raw number and hoping it's enough.
- **Per-entity world overlays** (health bars, name tags, chat bubbles, chant text) all go through one place client-side: `Chaos.Client/Rendering/EntityOverlayManager.cs` - a `Dictionary<uint, TOverlay>` keyed by entity ID per overlay type, with a consistent Add/Update/Remove/Draw lifecycle and a shared `ResolveOverlayOffset` for positioning above an entity's sprite. A new per-monster indicator (e.g. a visible stack counter) is a good fit for this exact pattern client-side - but there's currently no generic server→client channel for "entity X has N stacks of arbitrary status Y," only whatever's piggybacked on specific existing packets (health % on damage, etc). The overlay rendering itself is the easy half; a new indicator that isn't already covered by an existing sync point needs real wire-protocol work too, not just a new `UIElement`.
- **Random-target-selection AI logic must persist its pick, not re-roll every tick.** `AggroTargetingScript`'s Delirium-confusion branch used to call `Target = null` then pick a fresh random candidate every time its ~250ms update timer elapsed - the monster's target flickered constantly and never stayed still long enough to actually close distance and land a hit, which read as "the confused target doesn't attack anything." Fixed by keeping the current target as long as it's still a valid candidate (alive, in range, visible) and only re-rolling when it isn't. Same shape applies to any future "attack a random nearby X" mechanic - roll once, stick with it, re-roll only on invalidation.

## Test infrastructure gotchas

- **`FunctionalScriptRegistry.Scripts` is a single `private static readonly ConcurrentDictionary` shared across the ENTIRE test process**, not per-instance despite every test file constructing its own `new FunctionalScriptRegistry(...)`. Any test class whose script-under-test transitively calls `SomeDefaultScript.Create()` (which resolves through this same static registry) needs to register that key in its OWN static constructor - relying on some *other* test class happening to have registered it first is fragile and order-dependent. Found via `AscensionBossDeathScriptTests` (needs `DefaultLevelUpScript`, registered nowhere) passing or failing depending purely on whether an unrelated new test file elsewhere in the assembly shifted test discovery/scheduling order enough to change which static constructors ran first. If you add a new test file and something distant and unrelated starts throwing `KeyNotFoundException: Script with key 'X' not found`, this is why - fix it by adding the missing `registry.Register(...)` to the failing test class itself, not by reverting whatever you just added.
- **`MockAisling.Create`/`MockMonster.Create` set a `MapInstance` reference on the entity but do NOT register it in that map's spatial index or object collection.** Anything that queries the map for entities (`GetEntitiesAtPoints`, `GetEntitiesWithinRange`, `HasAislings`) will not find an entity created this way until it's also explicitly added via `map.AddEntity(entity, point)`. This includes the harness's own default `Source` Aisling - `MonsterScriptHarness`-based tests exercising a script that checks `Map.HasAislings` (e.g. `AggroTargetingScript`) need `harness.Map.AddEntity(harness.Source, Point.From(harness.Source))` explicitly, it is not done for you. Same root cause already noted for `MockMonster` in the Ragnarok/Divine Verdict tests; applies equally to Aislings.
- **`CreatureType.WalkThrough` passability is asymmetric, not "everyone walks through it"**: per `CreatureTypeExtensions.WillCollideWith`, an Aisling never collides with a WalkThrough entity, but a Normal-type creature (i.e. a monster) always does. This is why decoys/lures (Trickster's mirror_image_decoy, Fire Wall's elemental_hazard) work as monster-aggro bait despite being WalkThrough - real monsters still bump into them and can't path through, only players pass freely. If you want something genuinely passable for *everyone* (players and monsters both), `WalkThrough` alone doesn't get you there - the collision matrix would need a real change, which has wide blast radius across every existing WalkThrough entity in the game, not just the one you're touching.
- **`AoeShape.FrontalCone`'s width at the closest row is fixed regardless of `Range`** - `ConalSearch` widens going *away* from the source, but the immediately-adjacent row is always just 3 tiles (directly ahead + one diagonal each side); increasing Range only widens rows further out, it can never make melee-distance coverage wider, and a cone can never include a tile directly beside the caster (perpendicular to facing) at any range - that's outside its angular spread by definition. `FrontalDiamond` is a strict *subset* of `FrontalCone` at the same Range (it additionally filters by Manhattan distance), not a wider alternative - don't reach for it expecting more coverage. For "hits everything nearby regardless of facing" (a real sweep/spin motion), `AoeShape.Circle` centered on the caster is the right tool, not a frontal shape at all.
- **A freshly-mocked `IMonsterScript`/`IAislingScript` returns `false`/`default` for any unconfigured method** - `MonsterScriptBase`'s real `CanSee => true` default does NOT apply to a mocked script instance (Moq's own default behavior wins, not the interface's C# default implementation). Anything that calls into `Subject.CanSee(...)`/`Subject.IsHostileTo(...)` on a mock monster/aisling needs an explicit `MockMonster.SetupScript(subject, mock => mock.Setup(s => s.CanSee(...)).Returns(true))` (or the Aisling equivalent) or the check silently always fails, filtering out every candidate/target with no obvious error.

## Workflow

- Standard build/restart cycle: stop whatever's on port 5000, `dotnet build Chaos.slnx --nologo` and confirm `0 Error(s)`, run the server, grep its log for `error|exception|fail` (excluding lines containing `warning`).
- **PowerShell BOM gotcha**: `Set-Content -Encoding utf8` in Windows PowerShell 5.1 writes UTF-8 **with BOM**, which the JSON parser chokes on (`'0xEF' is an invalid start of a value`). Prefer the `Write`/`Edit` tools for JSON; if you must use PowerShell to write JSON, verify with a hex check (`EF BB BF` prefix = corrupted) or write via `[System.IO.File]::WriteAllText(path, content, (New-Object System.Text.UTF8Encoding($false)))`.
- **PowerShell + existing collections is landmine territory**: wrapping an already-existing `List<T>`/other `IEnumerable` in `@(...)` when passing it as a bare positional argument to a user-defined function can corrupt parameter binding in ways that are hard to diagnose (silently reports the wrong error, or the wrong line). Prefer named parameters (`-ParamName $value`) for anything beyond trivial scripts, or just do it in C# instead — `ConvertTo-Json` also silently collapses a single-element array into a bare object, which will corrupt any JSON file expected to stay an array. For anything that reads/writes real save-file JSON, a small C# console tool using `System.Text.Json.Nodes` is safer than PowerShell.
- Never commit or deploy without being explicitly asked. This repo has a live production deployment (git push → SSH pull → `dotnet build` → restart the systemd service) — treat any request to touch it as a distinct, higher-stakes ask from local testing.
- `Data/Configuration/Access/*/password.txt` is gitignored and untracked (per-account runtime credential data, not source) — don't re-add it.

## Ascension progression system — architecture and patterns

- **Level-cap enforcement has exactly TWO chokepoints**, both must be updated together: `DefaultExperienceDistributionScript.GiveExp` (stops feeding XP once capped) and `DefaultLevelUpScript.LevelUp` (defense-in-depth, blocks direct callers). Both now call `DefaultLevelUpScript.GetFloorLevelCap(aisling)` which reads `Trackers.Counters["highestFloorCleared"]` and returns the per-floor cap from `AscensionOptions.Instance`.
- **Ability evolution uses remove+add at preserved slot, not a "Replace" method.** `PanelBase` has no `Replace(slot, newObj)`. The correct pattern is: `TryGetRemoveByTemplateKey(oldKey, out old)` → `factory.Create(newKey)` → `TryAdd(old.Slot, newObj)`. The client's action bar is slot-indexed so this automatically preserves bar position. Both operations broadcast to observers so the client sees a seamless swap. See `AbilityEvolutionHelper` for the reusable utility.
- **AccountBound = true prevents BOTH trading AND dropping.** `NoTrade = true` alone still allows the item to be dropped (locked to the dropper). For a truly non-disposable item (Ascension Ticket), use both flags together plus `PreventBanking = true`.
- **`Trackers.Counters` monotonic-increment pattern prevents duplicate grants.** The established pattern (see `sorcererTierGranted`, `highestFloorCleared`, `ticketsClaimedTier`) uses a counter that only increases — check `if (counter < target) { grant; counter = target; }`. This is idempotent and safe against reconnect/retry.
- **Repeat-boss reward suppression uses `Subject.Contribution.Clear(participant)`.** `AscensionBossDeathScript` removes already-cleared players from the Contribution list BEFORE `DeathScript` runs (relies on `scriptKeys` ordering: `"AscensionBossDeath"` must be listed before `"Death"` in the boss monster template). This causes `DeathScript` to naturally exclude those players from XP/drop distribution without modifying `DeathScript` itself.
- **`CompositeMonsterScript.OnDeath` fires scripts in `scriptKeys` order.** If script A must modify state that script B reads, A must appear earlier in the `scriptKeys` array. This is how `AscensionBossDeath` suppresses rewards before `Death` processes them.
- **`ClassProgressionProvider` is the data-driven registry for all per-class progression.** Add a `{ClassName}.json` file to `Data/Configuration/Progression/` with tier entries. For specializations, use `{ClassName}_{AdvClassName}.json`. The trainer script is generic — it reads this data rather than hardcoding per-class logic.

## Equipment progression template conventions

- **Weapons** are per-class with numeric tiers: `{class}_wep_{1-10}` (e.g. `assassin_wep_3`). The heavy-melee classes use `WeaponMaster` weapons: **Berserker → `wm_blunt_{1-10}`** (axes thematically), **Slayer → `wm_twohanded_{1-10}`**, **Valkyrie → `wm_polearm_{1-10}`**. These assignments are locked.
- **Armor** is per-class per-floor with gendered variants: `fl{N}_armor_{class}_{m/f}` (e.g. `fl3_armor_berserker_f`). Any NPC or system that grants armor must check the player's gender to give the correct variant.
- **Accessories** use 10 named sets matching the locked floor themes across 7 slot types (belt, boots, earrings, gauntlets, greaves, necklace, ring). Floor-to-set mapping (LOCKED): I=wayfarer, II=verdant, III=mirageveil, IV=gravehollow, V=snowplume, VI=pearlshade, VII=cinderfell, VIII=sunkvault, IX=rosequartz, X=sundown. Template key pattern: `{setname}_{slottype}` (e.g. `gravehollow_belt`). All sets currently have identical placeholder stats — real stat values are a pending balance pass.
- **Template key lookup is case-insensitive and filename-based** — the folder structure is for human organization only. Two templates with the same filename under the same template type root will silently collide (first match wins).

## Evolving ability refactoring pattern (separate I/II/III/IV templates)

The locked Ascension design requires each evolving ability to exist as separate templates (`ability_i`, `ability_ii`, `ability_iii`, `ability_iv`) with tier-specific behavior configured via `scriptVars`, NOT a single template using `Subject.Level`-based `GetTierValues()`.

**Refactoring an existing evolving ability script:**
1. Identify what `GetTierValues()` returns (the tier-specific tuple of values).
2. Add each value as a new `scriptVars` property in the `#region ScriptVars` block.
3. Replace `var tier = GetTierValues();` with direct reads: `var rushDistance = RushDistance;` etc.
4. Remove the old `GetTierValues()` method entirely.
5. Create 4 template JSON files (`ability_i.json` through `ability_iv.json`) in the same `Skills/{Class}/` folder, each with different `scriptVars` values matching the locked tier behavior.
6. Set `"levelsUp": false` and `"maxLevel": 100` on tiered templates (they don't level internally — evolution IS the progression).
7. Keep the original un-tiered template (`ability.json`) for backward compatibility with the test/master trainer NPC — it can retain `levelsUp: true` as a "all-in-one" version for testing.
8. The `ClassProgressionProvider` JSON references the tiered keys (`ability_i` → `ability_ii` etc.) via `skillEvolutions`/`spellEvolutions`.

**Gender-aware equipment granting:** The `AscensionEquipmentVendorScript` resolves `{g}` in template keys to `m` or `f` based on `source.Gender`. Armor vendor TierItemKeys should use the placeholder pattern (e.g., `fl3_armor_berserker_{g}`) rather than duplicating entries or hardcoding gender checks elsewhere.
